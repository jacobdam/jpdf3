## Method
Four fresh reviewer subagents ran in parallel, each given only its area, the commit range and CONSTITUTION.md:
- security review of the engine, syntax, CLI and limits
- security review of the tooling (Arlington vendoring, web license checker, bench, CI, xtask)
- code review of the `jpdf-traits` conformance suites, rebuilding audit 0001's six proven toys
- code and process review of everything else

The reviewers proved their claims with:
- crafted PDFs (release `jpdf-cli`, `/usr/bin/time -l`) and a probe crate on top of `jpdf-engine`
- a scratch copy of `apps/web` with a fake dev-only MPL-2.0 package, run through a real `vite build`
- toy adapters in a scratch copy of `jpdf-traits`, plus an independent full inflater as a soundness control

Everything ran under `target/scratch/`; no tracked file was modified. `cargo mutants` ran alongside. I did the
housekeeping myself.

## Main findings
1. **The web license checker can be bypassed (#112, 2 high, 1 medium).** Each of these printed `licenses: ok`, and the
   tool package's marker reached `dist/`:
   - a relative import of a file with an unscanned extension (`./a.mod`, `./c.JS`), which Vite parses as JS
   - `import.meta.glob("/node_modules/…")`, which the import regex never matches
   - `.pcss` / `.postcss` / `.sss` files, which Vite treats as CSS

   CONSTITUTION 10 (shipped artifacts use the strict licenses only) currently rests on this check. The durable fix is
   #99 (Rollup's module graph); #112 closes the proven holes first.
2. **Conformance suites still accept broken adapters (#116, #117, #81).** Proven toys that pass at fa63ae1:
   - an inflater that can't decode Huffman codes longer than 9 bits (high)
   - an AES-CBC whose chain resets every 4 blocks, which also reuses the IV on write (high)
   - a font backend with no recursion guard, when the "hostile" glyph is dull junk that gives `Malformed` (high)
   - medium:
     - a PKCS#7 check that reads only 2 bytes
     - wrapping hash length counters (only SHA-256 sees > 1000 bytes)
     - raster working bytes that leave out masks and images
     - image: no salvage check and no option coverage (JBIG2 globals, CCITT K, JPEG options)

   Audit 0001's image toy (tolerance 255 with an all-zero decoder) still passes; #81 is open. All of this must land
   before #16 admits an adapter.
3. **A limit can be exceeded (#113).** Names and odd-length hex strings decode 1 byte past
   `max_string_bytes_per_parse` per token (check before push, never after the last byte). Memory stays bounded (about
   2 MB per parse), but the limit doesn't hold. No boundary test covered these tokens. Also, the CLI spec's "≤ 3.4 s
   for every adversarial file" is false: look-ahead re-lexes and re-classifies one 510 MB token, which takes 6.84 s.
4. **The clamp holds only at `Document::open` (#114).**
   - The sub-limit structs (`RasterLimits`, `FontLimits`, `DecodeLimits`) have public fields and reach backends
     unclamped.
   - `XrefDocument::parse` and `flat_page_count` are public and take unclamped limits.
   - A debug engine on a 512 KiB macOS secondary thread aborts at the default depth of 256 (it needs about 1 MiB).
5. **Missing exact-boundary tests (#87).** These have no at-limit/one-past pair:
   - `max_file_size` (engine)
   - `max_pages`
   - `max_objects_per_parse`
   - `max_objects_per_document`
   - `max_xref_entries`
   - the lex budget
   - the raster dash count
6. **Process (retro 0002).**
   - TICK §2 puts `security` issues (d) above a due audit (g). With 6+ security issues open the audit can slip for
     many sessions. It slipped one session this time: #110 was picked after the 10th merge. STATUS listed the audit
     first, which TICK doesn't allow.
   - STATUS is written inside the PR it describes, so "In flight: PR #N" is stale as soon as it merges.
   - `specs/_TEMPLATE.md`'s `Area:` list lacks `tooling`.

   Templates and TICK change only in retros, so these are inputs to retro 0002 (due 2026-11-28).

## Test strength (cargo mutants 27.1.0)
On the diff since audit 0001 (`--in-diff`), for jpdf-syntax, jpdf-engine, jpdf-cos, jpdf-cli and jpdf-arlington, with
the tests of all five:

| Mutants | Caught | Missed | Timeout | Unviable |
|---|---|---|---|---|
| 177 | 163 | 8 | 1 | 5 |

That is 96% (164/171) of viable mutants caught, with the timeout counted as caught.

The real survivors are in tools/arlington:
- the pinned-blob size cap (`fetch.rs:265`, `>` survives as `>=`)
- the bad-notice-name check (`vendor.rs:298`)

Five are equivalent mutants:
- SHA-1 `|`→`^` on disjoint Ch terms and in Maj (3)
- the Linux-only `OPEN_FLAGS`, which isn't compiled on macOS (2)

The timeout (`sha1.rs:25`) is an infinite padding loop.

jpdf-traits, on the diff in `limits.rs`, `raster.rs` and `conformance/mod.rs` (the boundary helper): 79 mutants. 74 were
caught, 1 missed and 4 unviable, so 99% of viable mutants were caught. The miss is real:
- `Pixmap::pixel` survives `||`→`&&`, because no test reads with only x out of range, which returns a pixel from the
  next row (→ #117).

A full in-diff run over the suites would have been 626 mutants at about 26 s each, which is too slow for one session.
The suite files were covered by the toy-adapter review instead.

Not run: xtask and tools/bench (their tests take ~45 s per mutant). The suites were reviewed by hand with toys instead.
