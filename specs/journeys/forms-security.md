# Journeys: forms and security

Areas `FM` (interactive forms) and `SC` (document security: passwords, permissions, certificate
encryption, true redaction, removing hidden information). PLAN §4 (Forms; Security &
signatures), feature groups F-FM-1, F-SC-1 and the redaction and metadata-scrub half of F-ED-4
in [specs/TRACE.md](../TRACE.md). Signatures and platform conventions are written in #42.
Inventory and coverage: [RESEARCH.md](RESEARCH.md). Format: ops/judge/CONTRACT.md §4.
Milestones (PLAN §8): forms are M7; passwords and permissions are M6 (writer); certificate
encryption is M9 (it needs the CMS code of the signatures milestone); redaction and removing
hidden information are M8.

Shared rules for every journey in this file. The reader rules at the top of
[reader.md](reader.md) (fixtures, web network policy, file-handle adapter, engine-owned logic,
browser-safe shortcuts, engine gate, fixed seeds), the annotate rules in
[annotate.md](annotate.md) (author name, counting, undo keys, pointer input in tests) and these
rules from [pages-edit.md](pages-edit.md) also apply: page ranges, save and verify, write and
verify, history is honest, permissions.

- **Engine owns forms and security.** Field lookup, hit-testing, focus and tab order, value
  parsing, formatting, calculation, appearance generation, field creation and editing,
  flattening, permission checks, password processing (SASLprep, key derivation), encryption and
  decryption, redaction geometry and content removal, and finding hidden information all happen
  in the Rust engine (CONSTITUTION 6). The native layer sends pointer and keyboard events, typed
  text and dialog values, and displays the engine's results. Every value from it (field names,
  values, option lists, sizes, colors, passwords, permission choices, rectangles, certificate
  bytes) is validated by the engine and rejected with a typed error when out of range
  (CONSTITUTION 5). Where a journey says a control is disabled, the test also calls the binding
  directly and expects the engine's typed error.
- **No scripts, ever** (CONSTITUTION 7). The engine never runs JavaScript. It recognizes a small
  set of standard form function calls by parsing the script text with a strict grammar that
  accepts only the exact call forms listed in J-FM-05 and J-FM-06 with literal arguments; any
  other script text (extra statements, comments, variables, string concatenation, unknown
  functions) is not run, the field behaves as if it had no script, and a one-time notice per
  document says how many fields have scripts that jpdf does not run.
- **Field values check.** "The fields read …" means: after reopening, our engine, `qpdf --json`
  (its `acroform` section) and `mutool show <file> <field object>` report the same `/V` for each
  named field (text strings compared after decoding PDFDocEncoding or UTF-16BE), and each
  widget's `/AS` (buttons) matches.
- **Appearance check.** For every widget the journey filled or created: the widget has an
  `/AP /N` appearance stream generated by the engine (ISO 32000-2 §12.7.4.3 for variable text,
  §12.7.5.2 for buttons), `/AcroForm /NeedAppearances` is absent or false, and the MuPDF and
  Poppler renders of the widget's `/Rect` at 72 dpi match our render within the render-ratchet
  tolerance and differ from the same area before the change. External tools therefore draw our
  appearance and never regenerate their own.
- **Form fixtures.** Unless a journey says otherwise, fixtures are generated by the harness with
  an `/AcroForm` whose `/DR` holds Helvetica (`/Helv`, standard 14, WinAnsiEncoding) and whose
  fields have `/DA (/Helv 0 Tf 0 g)` (auto size); field names are given in each journey as
  fully qualified names (ISO 32000-2 §12.7.4.2).
- **Redaction check** (J-SC-07 … J-SC-10). Fixture areas carry unique sentinels: text strings
  (`red-secret-n`, written once as literal strings and once as hex strings in the content), and
  image pixels and vector strokes in a marker color (DeviceRGB 0.004 0.996 0.012) that appears
  nowhere else in the file. After applying and saving (always a full rewrite, see J-SC-07):
  1. Removed everywhere: no sentinel appears in our text extraction, `pdftotext`, `mutool draw
     -F txt`, the raw output bytes, or the bytes of `qpdf --qdf --object-streams=disable` output
     (every stream decompressed), searched as ASCII, as UTF-16BE and as hex digits; no image
     extracted with `pdfimages -all` has a pixel of the marker color; the MuPDF and Poppler
     renders at 150 dpi have no marker-color pixel.
  2. Painted: every pixel of each redacted area in the MuPDF, Poppler and our renders at 150 dpi
     is the area's fill color (default black), except glyphs of the overlay text when one is set.
  3. Kept: every sentinel outside the areas (`keep-n`) is still extracted by `pdftotext -bbox`
     with its box within 0.5 pt of where it was; the renders outside the areas (each area grown
     by 2 pt, and leaving out the rectangles of fields and annotations that the journey changed
     through "Remove these too") match the renders before redaction within the render-ratchet
     tolerance; a field cleared that way gets a regenerated `/AP /N`.
  4. Write and verify holds (one revision; `qpdf --check` clean).
  5. Residue: page thumbnails (`/Thumb`) of redacted pages are removed; fonts used by removed
     text are re-subset so that glyphs and `/ToUnicode` entries no remaining text uses are gone;
     images re-encoded by the engine drop JPEG metadata segments (EXIF, XMP, embedded
     thumbnails) and `/Alternates`; crash-recovery copies of the document (#42) that hold
     pre-redaction content are deleted when the redacted file is saved (tested once #42 defines
     crash recovery; not part of the M8 gate before that). The font check compares the glyph
     sets of each font program before and after (fonts extracted with `mutool extract`, glyphs
     listed with fontTools) against the glyphs of the remaining text. Known residual risk,
     stated in the redaction help text: the width of the gap left by removed text is kept so
     that the remaining text does not move.
- **Passwords.** New passwords are entered twice (password and confirm), are prepared with
  SASLprep and limited to 127 UTF-8 bytes after preparation (ISO 32000-2 §7.6.4.3.3); when a
  password is set, the engine rejects a longer one with a typed error instead of truncating it,
  and rejects text that SASLprep prohibits (control characters, unassigned code points, bidi
  violations). When a file is opened or unlocked, a longer password is truncated to 127 bytes as
  the standard's algorithm does, so files made by other tools still open. Passwords are never
  stored, logged, put in recent files or kept after the document closes; each journey that types
  a password ends with the J-RD-04 storage search for it. Key material and file keys come from
  the platform's secure random source through the engine's random trait.
- **Encryption writing** (CONSTITUTION 17). We create only the AES-256 standard security
  handler (`/V 5 /R 6`, crypt filter `/AESV3`, `/Length 256`, ISO 32000-2 §7.6.4) or, for
  certificate encryption, the public-key handler with `/AESV3` (§7.6.5). RC4, AES-128 and
  revisions 2–5 are read (J-RD-30) but never created. A file that already uses an older handler
  keeps it as it is through incremental saves (the update is encrypted with the file's own
  key); a full rewrite of such a file upgrades it to AES-256 R6 with the same passwords and
  permissions when the permissions password is known (entered, or the file restricts nothing,
  i.e. every permission bit is set, and the open password was entered; the same condition
  enables Change security and Remove security, J-SC-03, J-SC-04), with a notice that the encryption was upgraded;
  otherwise the full rewrite keeps the original encryption dictionary, file key and first `/ID`
  element, and a notice suggests Change security (J-SC-03) to upgrade. `/P` is written with bits 1–2 clear, bits 7–8 and 13–32 set, and
  bit 10 set (Table 22: accessibility extraction is always allowed); `/Perms` is present and
  matches `/P`; `/EncryptMetadata` is true. Every change of encryption (adding, changing,
  removing) re-encrypts every string and stream, so it is written as a full rewrite with no
  earlier revisions, and the dialog says so before saving. Two encryptions of the same file with
  the same passwords produce different `/O`, `/U`, `/OE`, `/UE` and `/Perms` values (fresh
  salts and file key).
- **Signed files.** Changes that invalidate existing signatures (any full rewrite of a signed
  file) warn that the signatures will no longer verify and default to Cancel, as in J-OS-02.
  Certification permissions (DocMDP) are covered with the signature journeys (#42).

## J-FM-01: Fill text fields
- milestone: M7
- platform: web, macos
- test: e2e.web.fm_fill_text, e2e.macos.fm_fill_text

Steps: open a form fixture with text fields `name` (single line, `/Q 0`), `address`
(multiline, `/Ff` bit 13), `zip` (comb, `/MaxLen 5`, `/Ff` bit 25), `code` (`/MaxLen 4`, not
comb), `pin` (password, `/Ff` bit 14), `notes` (`/DA (/Helv 12 Tf 0 g)`, fixed size) and
`city.home` and `city.work` (two fields under the non-terminal `city`), plus a second widget
of `name` on page 2 (the same field, two widgets); every field starts empty → click `name` on page 1 and type `Ada Lovelace`
→ press Tab → the page 2 widget of `name` shows `Ada Lovelace` → type three lines into
`address` separated by Return → type `123456` into `zip` → it holds `12345`, one digit per comb
cell → type `ABCDE` into `code` → it holds `ABCD` → type `s3cret` into `pin` → it shows six
bullets → type `Đặng Ελλάδα` into `notes` (characters Helvetica's WinAnsiEncoding lacks) → a
notice says a fallback font was used for this field → type into `city.home` and `city.work` →
save and verify (incremental) → the fields read: `name` = `Ada Lovelace`, `address` with two
line feeds, `zip` = `12345`, `code` = `ABCD`, `notes` = `Đặng Ελλάδα` stored as UTF-16BE with BOM,
`city.home` and `city.work` as typed; `pin` has no `/V` in any revision of the saved file (ISO
32000-2 §12.7.5.3: password values are never stored) and its widget appearance shows six
bullets → the appearance check holds for every filled widget; `notes` draws with a subset of the
bundled fallback font added to the widget's appearance resources, and `/DA` is unchanged →
reopen → `pin` is empty.
Error branch: the binding call setting `zip` to `1234567` and `code` to a 10 000-character
string each returns the engine's typed error (over `/MaxLen`); a value longer than `Limits`
string length is rejected for a field without `/MaxLen`; a value with U+0000 or an unpaired
surrogate (web) is rejected; type into `name` and press Esc → the typing is discarded, the
field shows the value it had when it got focus, and it loses focus (shortcuts.md rule 9).

## J-FM-06: Calculated fields with the built-in functions
- milestone: M7
- platform: web, macos
- test: e2e.web.fm_calculate, e2e.macos.fm_calculate

Steps: open a fixture with number fields `a`, `b`, `c` (each `AFNumber_Format(2, 0, 0, 0, "",
false)`), and calculated read-only fields (each also with `AFNumber_Format(2, 0, 0, 0, "", false)`)
`sum` = `AFSimple_Calculate("SUM", new Array("a", "b", "c"))`, `avg` (`"AVG"`, same fields), `min`, `max`, `prd` (`"PRD"`) and `total` =
`AFSimple_Calculate("SUM", "sum, prd")` (the comma-separated string form), with `/AcroForm /CO`
listing `sum, avg, min, max, prd, total` → type `0.1` into `a`, `0.2` into `b` and leave `c`
empty → after each committed value the calculated fields update: `sum` shows `0.30` (decimal
arithmetic in the engine, not binary floating point) and `avg` shows `0.10` (an empty field
counts as 0, as consensus viewers do), `prd` shows `0.00`, `total` shows `0.30` → type `3` into
`c` → `sum` `3.30`, `avg` `1.10`, `min` `0.10`, `max` `3.00`, `prd` `0.06`, `total` `3.36` →
undo the last value → every calculated field shows its previous value again → redo → save and
verify (incremental; field values check: `sum` `/V (3.3)`, `avg` `(1.1)`, `min` `(0.1)`, `max`
`(3)`, `prd` `(0.06)`, `total` `(3.36)`; the appearance check holds for each calculated field;
`/CO` is unchanged).
Error branch: a fixture where `x` sums `y` and `y` sums `x` (a cycle through `/CO`) → the
engine computes each field at most once per change in `/CO` order and shows a notice that the
form has a circular calculation; a calculation naming a field that does not exist treats it as
0 and lists it in the notice; results are rounded half-even to 15 significant digits before
formatting (`avg` of 0.7, 0 and 0 stores `0.233333333333333`); a result past ±10^15 shows a
typed range error in the calculated field instead of a number; typed values `1e400`, `NaN`,
`Infinity` and a value with more than 15 significant digits are rejected by the engine's number
parser,
and `-0` is accepted and shown as `0.00`; `AVG` over an empty field list (`new Array()`) gives
`0` (no division by zero); a `/CO` holding
more entries than `Limits` form fields, a non-field object or the same field twice opens with
calculation off and a notice.
